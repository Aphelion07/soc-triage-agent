# soc-triage-agent

**A SOC alert-triage agent that knows when to escalate to a human instead of acting alone, measured against a rule-based baseline and a no-tools ablation - not assumed better because it's an LLM.**

## Why measure this instead of assuming an agent should decide

An autonomous SOC agent that occasionally auto-closes a real incident isn't a triage assistant, it's an incident waiting to be found weeks later in an audit. So the question this project asks isn't "can an LLM triage alerts" - it's "how do you know when to trust it, and what does trusting it cost you when it's wrong."

That means two things had to be measured, not assumed: whether the agent actually beats simpler alternatives at the raw classification, and whether its own confidence is a trustworthy signal for the one decision that matters most - when to hand an alert to a human instead of acting alone.

```
rule-based baseline:      93.3% accuracy   0.0% missed incidents   45.7% automated
LLM agent, with tools:    86.7% accuracy   0.0% missed incidents   69.7% automated
LLM agent, no tools:      62.0% accuracy   0.0% missed incidents   71.7% automated
```

The baseline is more accurate than the LLM agent. Neither ever silently drops a real incident. But accuracy isn't the whole story - see finding 2 for the number that actually changed my mind about which one I'd trust.

## What it compares

Three ways to turn one alert into a verdict (malicious?, severity, confidence), all scored against the same held-out ground truth and the same deterministic [escalation policy](#the-escalation-policy-is-not-the-agents-call):

| | reasoning | context | needs a GPU |
|---|---|---|---|
| **Baseline** (`baseline.py`) | fixed weighted score | reads the same facts directly | no |
| **Agent, no tools** (`triage_agent.py --no-tools`) | LLM, one shot | alert text only | no (runs via Ollama) |
| **Agent, with tools** (`triage_agent.py`) | LLM, tool-calling loop | calls 3 lookup tools first | no (runs via Ollama) |

The agent is built on [`agent-core`](https://github.com/Aphelion07/agent-core) - this portfolio's from-scratch agent framework - rather than reimplementing an LLM-calling, tool-registry, retry-hardened HTTP client a fourth time. See [Design decisions](#design-decisions) for why it doesn't reuse agent-core's `ReActStrategy` too.

## The dataset

300 synthetic SOC alerts across 5 detection rules - `ssh_auth_failures`, `sql_injection_pattern`, `xss_pattern_waf`, `port_scan_detected`, `outbound_beacon` - generated by [`data/build_alerts.py`](data/build_alerts.py), balanced 30/30 malicious/benign per rule.

Every rule fires on **both** a genuine incident and a benign look-alike that trips the same detection logic for an innocent reason: the signature that catches SSH brute-forcing also catches a developer who mistyped their password, the WAF rule that blocks real SQL injection also blocks a book search for a title containing "SELECT". That's the actual shape of SOC alert fatigue, and a dataset where the rule alone determined the label would let a lookup table pass for a triage agent.

Two categories are deliberately harder. `port_scan_detected` gives a real scan and a noisy internal health-check similarly bursty event history, so volume alone doesn't discriminate. `outbound_beacon` gives malicious C2 traffic a lower threat-intel hit rate (30%, vs 50-60% for the other attack types) since new C2 infrastructure is often unlisted - the same reason malware beaconing was the hardest class in this portfolio's [`finetune-lora`](https://github.com/Aphelion07/finetune-lora) project, reached from the agent side this time instead of the classifier side.

## Findings

All figures: `qwen3:8b` via Ollama, RTX 5080, 300 alerts, escalation threshold 0.7 unless noted. Reproduce with `python data/build_alerts.py && soc-triage baseline && soc-triage agent --model qwen3:8b`.

### 1. Tools are not decorative: 24.7 points of accuracy live in the lookups

| | accuracy | automation | missed incidents |
|---|---|---|---|
| agent, no tools | 62.0% | 71.7% | 0.0% |
| agent, with tools | 86.7% | 69.7% | 0.0% |

Taking away `asset_criticality_lookup`, `threat_intel_lookup` and `alert_history_lookup` and asking the model to decide from the alert text alone drops accuracy by nearly 25 points. Both configurations still never miss a real incident (finding 3 explains why that number is less reassuring than it sounds), but without evidence-gathering, "an agent with tools" is doing most of the actual work an LLM contributes here - the model's own judgement on raw alert text is closer to a coin flip with a safety bias than a classifier.

### 2. The baseline is more accurate, but the LLM's mistakes are the ones a human is more likely to catch

Both approaches score `false_escalation_rate` at essentially the same number (31.3% vs 31.3%, coincidentally identical to three digits) and both hit 0.0% missed incidents. Read only that far and the two look interchangeable. They aren't:

| | total errors | error direction | not escalated (silently acted on) |
|---|---|---|---|
| baseline | 20 | 12 missed-then-escalated, 8 false alarms | **0** |
| agent, with tools | 40 | 0 missed, 40 false alarms | **29 (72.5%)** |

Every one of the baseline's 20 wrong verdicts still got caught by the escalation policy - its confidence score naturally sits close to the 0.5 boundary when the underlying signals are genuinely ambiguous, so a wrong call is also a *low-confidence* call, and the policy sends it to a human anyway. The LLM agent's 40 wrong verdicts are a different shape entirely: it never once calls a real incident benign, but when it wrongly calls a benign alert malicious, it's frequently very sure of it (confidence 0.85-0.95, severity `high` or `medium`) - confident enough to clear the escalation bar and get auto-actioned as if confirmed. 29 of its 40 mistakes never reach a human. The number that matters for a human-in-the-loop system isn't "how often is it wrong" - it's "how often is it wrong *and confident*," and on that number the less-accurate baseline is safer.

### 3. Sweeping the threshold shows the baseline's safety is threshold-dependent; the agent's isn't

| threshold | baseline missed incidents | agent missed incidents |
|---|---|---|
| 0.3 | **8.0%** | 0.0% |
| 0.5 | **8.0%** | 0.0% |
| 0.7 | 0.0% | 0.0% |
| 0.9 | 0.0% | 0.0% |

Turn the baseline's confidence threshold down to chase more automation and real incidents start silently slipping through - at 0.3 or 0.5, 8% of genuine incidents get auto-closed as benign, because the baseline's score can legitimately drop below the low threshold on a real attack with unusually weak signals (clean threat intel, low-criticality host, low event volume). The LLM agent's missed-incident rate stayed at exactly 0.0% at every threshold tested from 0.3 to 0.9 - it never assigns low confidence to a genuinely malicious alert, so loosening the policy costs it false-escalation waste, not safety. Neither property is free: the agent pays for that robustness with the confident-false-alarm problem in finding 2, at every threshold. Whoever sets this threshold in a real deployment needs both tables, not just one.

### 4. Bug found & fixed: `agent-core` had no `py.typed` marker

Wiring `agent-core` up as this project's first real downstream dependency (`agent-core @ git+...` in `pyproject.toml`) immediately surfaced that mypy silently stopped type-checking anything imported from it - the package has full inline type annotations and passes `mypy --strict` inside its own repo, but without a `py.typed` marker file, a *consumer's* mypy run treats the whole thing as untyped per PEP 561. Fixed upstream: `agent-core` now ships `src/agent_core/py.typed`, verified present in the built wheel before pinning this project's dependency to the commit that includes it.

## The escalation policy is not the agent's call

`escalation.py` is deliberately dumb: fixed arithmetic on a verdict's own reported confidence plus the alert's independently-known asset criticality, with no LLM call in the loop. A model that gets to decide *for itself* whether it's confident enough to act alone is exactly the failure mode a human-in-the-loop gate exists to catch - self-assessed confidence is not the same thing as calibrated confidence, and finding 2 is a direct demonstration of that gap. The policy is a few lines of reviewable code specifically so the escalation decision can be audited without re-running anything.

A triage run that never produces a verdict at all (the model exhausts its step budget without calling `submit_verdict`) is treated as confidence `0.0`, which forces escalation under any real threshold - the safe default is "ask a human," not "assume benign because the loop ran out of steps."

Both `baseline` and `agent` expose `EscalationPolicy`'s fields as flags - `--confidence-threshold` and `--always-escalate-criticality` (repeatable, or comma-separated) - so the threshold sweep in finding 3, and any run with a different always-escalate set, is reproducible from the command line instead of editing `escalation.py`'s defaults.

## Quickstart

```bash
git clone https://github.com/Aphelion07/soc-triage-agent
cd soc-triage-agent
uv venv && uv pip install -e ".[dev]"
```

Generate the alert dataset and run the baseline (no GPU needed):

```bash
python data/build_alerts.py
soc-triage baseline
```

Run the LLM agent:

```bash
ollama pull qwen3:8b
soc-triage agent --model qwen3:8b
soc-triage agent --model qwen3:8b --no-tools   # the ablation in finding 1
```

Re-score a saved run at other escalation thresholds without touching the model again:

```bash
soc-triage sweep --verdicts results/agent_with_tools.json --thresholds 0.3,0.5,0.7,0.9
```

Or run a triage pass under a different escalation policy directly, without editing `escalation.py`:

```bash
soc-triage baseline --confidence-threshold 0.3 --always-escalate-criticality high,critical
```

Or with no GPU and no model at all - exercises the full tool-calling loop and escalation policy against a scripted backend, which is what CI's smoke job runs:

```bash
soc-triage agent --fake
```

## Design decisions

**Depends on `agent-core` as a real package, pinned to a commit.** `pyproject.toml` declares `agent-core @ git+https://github.com/Aphelion07/agent-core.git@<sha>` rather than vendoring or reimplementing its `Tool`/`ToolRegistry`/`LLMBackend`/retry-hardened `OllamaBackend`. Pinned to a specific commit rather than floating on `main` so a future change to `agent-core` can't silently change this project's behaviour or break its CI.

**Reuses `agent-core`'s primitives but not its `ReActStrategy`.** ReAct's loop is built to end in free text; triage needs to end in a structured, machine-checkable verdict a policy can act on. `triage_agent.py` writes its own small loop around `agent-core`'s `Message`, `Tool`, `ToolRegistry` and `LLMBackend` that forces a `submit_verdict` tool call instead of parsing free text - the reusable plumbing gets reused, the task-specific control flow doesn't get bent to fit a strategy designed for a different kind of answer.

**Confidence means "confidence in the verdict," not "probability of malicious."** Both the baseline and the agent report a single `confidence` in `[0, 1]` that reflects how sure the source is of *whichever way it decided* - 0.9 confidence in "benign" and 0.9 confidence in "malicious" are both high-trust verdicts. This is what makes one threshold meaningful for both directions in the escalation policy, instead of needing separate thresholds for false positives and false negatives.

**The threshold sweep re-scores saved verdicts instead of re-running the model.** A verdict and its confidence are produced once per alert; the escalation threshold only changes which of those saved verdicts get flagged for a human. `soc_triage.cli sweep` reads a prior run's output file and recomputes metrics in milliseconds - the same reasoning behind `agent-core`'s and `local-inference-bench`'s sweep designs in this portfolio.

## Testing

```bash
pytest -q --cov=soc_triage --cov-report=term-missing
ruff check . && ruff format --check . && mypy
```

46 tests, 99% coverage, mypy `strict`. Nothing touches the network or a GPU: the triage loop is tested against `agent-core`'s `FakeBackend` (a scripted tool call followed by a verdict, a plain-text response that gets nudged back toward `submit_verdict`, a malformed verdict, a step budget that runs out without one), and the escalation policy and metrics are tested against hand-worked examples rather than against the implementation's own logic.

## Limitations

- **One model, one hardware target.** All findings are `qwen3:8b` on one RTX 5080. A larger or better fine-tuned model could plausibly close the accuracy gap in finding 1-2 while keeping the same safety bias; that's untested here.
- **300 synthetic alerts, one seed.** Enough to see a 25-point tools ablation and a 0% vs 8% missed-incident gap clearly, not enough to bootstrap a tight confidence interval the way `agent-core`'s and `local-inference-bench`'s repeated-run sweeps do - a single run per configuration here, which the pattern in finding 3 (consistent across every threshold tested) partially offsets but doesn't replace.
- **The threat-intel and alert-history tools are synthetic and internally consistent by construction.** A real threat-intel feed lies, lags, and disagrees with itself across sources; these tools never do, which likely overstates how much a tool call actually helps in production.
- **The escalation policy's thresholds (confidence 0.7, always-escalate on `critical` severity or `critical` asset criticality) were chosen for a legible sweep, not tuned against an operational cost model.** A real deployment would set these against the actual cost of an analyst-hour versus the cost of a missed incident, which this project doesn't attempt to price.
- **"Missed incident" and "false escalation" don't capture every failure mode.** A confidently-wrong `malicious` verdict on a benign alert that clears the escalation bar (finding 2's 29 cases) isn't a missed incident and isn't a false escalation - it's a third failure mode, "auto-actioned on a false alarm," that this project's two headline metrics don't name on their own; finding 2 exists because the aggregate numbers alone hid it.
